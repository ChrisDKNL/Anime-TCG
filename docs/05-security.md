# Security Register

The single place where this project's security posture is written down: the controls that exist, the tier every change is assessed at, the test that tier requires, and a log of every security-relevant change. `security-officer` owns keeping it current; the manager refuses a PR whose security tier is not stated.

Threat model in one paragraph: the attacker is an ordinary player with a browser. They can edit anything client-side, replay or forge requests, submit hostile input, and try to read or change other players' data. They cannot read the server. Secondary attackers: a compromised dependency, and anyone on the internet probing the NAS. Out of scope: the owner's own machine, physical access.

## Security tiers: how much testing a change gets

Every PR states its tier in the template. `security-officer` can raise a tier, never lower it. The manager assigns the initial tier; disagreement goes to the owner.

| Tier | Applies to                                                                                                                                                                 | Review                                                                       | Required test                                                                                                                                                                                                                                                                                                      |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T0   | Docs, styling, copy, test-only changes with no data or network effect                                                                                                      | none                                                                         | none                                                                                                                                                                                                                                                                                                               |
| T1   | UI changes that display user or third-party data; new client-side fetches of existing endpoints                                                                            | `security-officer` checklist pass (minutes)                                  | A unit test that hostile strings (script tags, long input, RTL overrides) render as text                                                                                                                                                                                                                           |
| T2   | New or changed API endpoints, validation schemas, database migrations, new dependencies, CI/workflow changes                                                               | Full `security-officer` review                                               | Route tests for: schema rejection of bad/extra fields, authorisation (another user's id is denied), rate limit where applicable. New dependency: provenance check noted in the PR                                                                                                                                  |
| T3   | Authentication, sessions, password handling, invite codes, currency/ledger, pack grants and openings, game outcome logic, RNG, CSP/headers, compose/proxy/network exposure | Threat-model update in this file + full review + owner informed before merge | T2 tests plus an adversarial suite: replay, forged session cookie, concurrent double-spend / double-open, negative and overflow amounts, tampered outcome payloads, brute-force against the rate limit, and a dependency audit of anything new. For RNG and payouts: a statistical test against the published odds |

Severity decides depth: the test list above is the minimum, and the officer lengthens it when the blast radius is bigger than the tier's typical case. A T3 change never merges on the same day it is opened unless the owner says so in the PR.

Security tests live next to the code as `*.security.test.ts` and run in the normal test jobs (`quality` for `web/`, `api-tests` for `api/`), so a regression fails CI like any other test. Both jobs must be required checks in the live ruleset for that to hold.

## Open items

- 0.3 Retroactive `security-officer` review of the CI workflow, hooks and Dependabot config against this register.
- Decide tunnel vs. port-forward for the NAS (C15) before the first API deploy.
- With the C15 decision: the api trusts `loopback, uniquelocal`, so a LAN visitor can choose its own rate-limit key via `X-Forwarded-For`; once the hop count is fixed, narrow `trustProxy` to the proxy's address.
- Compose `secrets:` for `SESSION_SECRET`, `POSTGRES_PASSWORD_FILE`, `APP_DB_PASSWORD` and `INVITE_CODES` instead of plain environment variables (spec `accounts-api.md` §2 keeps it a separate chore).
- Throttle (C17, #23 finding 6, low): a miss recorded while a block is active resets the row to one failure and no block, in `recordFailure` of `throttle.ts` and in the `CASE` of `throttle-store.ts` alike; make both keep a `blocked_until` that is still in the future (`CASE WHEN auth_throttle.blocked_until > now THEN auth_throttle.blocked_until ...`), with a state-machine test and a store test that records a miss on a blocked row.
- Logging (#23 finding 4, owner decision): decide whether `login failed` keeps the typed login (operator sees who is attacked) or logs only the account id of a known login, since a password typed into the login field is logged today (spec §6.7 asks for the login).
- Logging (#23 finding 7, info): the `cause` the error serializer keeps is pg's `DatabaseError` with `detail`, `where` and `internalQuery`; Postgres puts the whole failing row in `detail` on a NOT NULL violation. Keep only `message`, `code`, `constraint` and `stack` of the cause before any table carries a secret column that could fail that way.
- Convention (#23, quality-controller): the POST/PATCH account routes accept and ignore a query string (proven harmless by `accounts.security.test.ts`); add `NoQuery` to them, and either declare the plugin-produced statuses (403 `bad_origin`, 429 `rate_limited`, 500 `internal`) in every route's `response` schema or write the 1a precedent into the fastify skill.
- Invite audit trail (#23, info): `invite_code_hash` is an unsalted SHA-256 of a short code; if the column is ever more than an audit trail, store an HMAC with `SESSION_SECRET` or a truncated digest.
- Logins (#23, info): uniqueness is case-folding only; consider NFKC-normalising `login_normalized` before a second real user can impersonate a first by confusable characters.
- Memory (C4): `UV_THREADPOOL_SIZE` is the real bound on concurrent Argon2id derivations (4 x 19 MiB); any change to it or to the api `mem_limit` goes through this register.
