# Security Register

The single place where this project's security posture is written down: the controls that exist, the tier every change is assessed at, the test that tier requires, and a log of every security-relevant change. `security-officer` owns keeping it current; the manager refuses a PR whose security tier is not stated.

Threat model in one paragraph: the attacker is an ordinary player with a browser. They can edit anything client-side, replay or forge requests, submit hostile input, and try to read or change other players' data. From 1c they also try to mint cards: open more packs than the allowance grants, replay or race an opening to be dealt twice, push the pity or Enchanted counters, or choose a pack's outcome. The server owns the allowance clock, both counters and every roll (C1, C10, C20); the client sends only an idempotency key. They cannot read the server. Secondary attackers: a compromised dependency, and anyone on the internet probing the NAS. Out of scope: the owner's own machine, physical access. From #35 every app change on `main`, Dependabot's auto-merged updates included, is built and run in acceptance on the dev station without a human step (Dependabot's after a 72-hour delay), so a compromised dependency is a live attacker there with acceptance's secrets and outbound network. From 1c web (#38) the browser talks to the app's own origin only (`connect-src 'self'`); its one remote load is card art from `s4.anilist.co`, and it renders AniList names and titles it receives from the api as isolated text. From item 2 they also try to mint or double-spend Karma: replay or race a recycle or a shop purchase to be credited twice or to get two packs for one debit, recycle a last copy or another account's card, send an amount or a price, overflow a balance, or loop shop packs through the recycler for profit. The server holds every value and every amount; each balance change is a ledger row written under the account row lock in the transaction of what it pays for (C11), and the owner's `audit-ledger` checks the ledger against balances, recycles and shop openings (C22). An attacker who can run SQL as the request role can still hide a forged recycle behind a forged reset on an account it has emptied first, so against a compromised api process the audit detects inconsistency but does not prove that nothing was minted (open item). From #42 two routes are public and unauthenticated (`GET /api/demo`, `POST /api/demo/open`): anyone on the internet can read the published odds and pool size and have the server roll demo packs that are never stored, so what they gain is load, bounded by `DEMO_RATE_LIMIT` and the global limit per address, and samples of a `crypto.randomInt` generator with nothing to learn from; no card, counter, session or account is reachable from them (C23). From #51 the browser drives the Karma actions: it sends only `{ requestId, themeId }` to buy and `{ requestId, characterId, rarity, count }` to recycle, holds each key in memory for one confirmation, never in storage or the address, and shows only balances the server sent, so editing the client changes what is displayed, never what is held (C1, C11, C20). From #53 the market is a trust boundary between two accounts: a purchase moves Karma and one card in a single transaction that locks both account rows in ascending id order, then the listing, then the card, so a listing sells once, credits its seller once and debits its buyer once, and purchases in opposite directions cannot deadlock (C11, C24); the browse route takes only enumerated filters, digit-string ids, a control-character-free search text of at most 10 terms matched as escaped `LIKE` patterns and its own re-checked cursor, and publishes no other account's login or id; and one person with several accounts is bounded, not detected, by the destroyed fee, the per-tier price bounds and the rolling 7-day window and pair limits, with `audit-market` as after-the-fact detection (C24, economy.md §10). From #60 the browser drives the market: it sends `{ requestId, characterId, rarity, price }` to list (the asking price is the only number, and the server bounds it), `{ requestId }` alone to buy and `{}` to cancel, holds each key in memory for one confirmation, never in storage or the address, and shows only the prices, fees, balances and limits the server sent (C1, C11, C20, C24).

## Security tiers: how much testing a change gets

Every PR states its tier in the template. `security-officer` can raise a tier, never lower it. The manager assigns the initial tier; disagreement goes to the owner.

| Tier | Applies to                                                                                                                                                                 | Review                                                                       | Required test                                                                                                                                                                                                                                                                                                      |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T0   | Docs, styling, copy, test-only changes with no data or network effect                                                                                                      | none                                                                         | none                                                                                                                                                                                                                                                                                                               |
| T1   | UI changes that display user or third-party data; new client-side fetches of existing endpoints                                                                            | `security-officer` checklist pass (minutes)                                  | A unit test that hostile strings (script tags, long input, RTL overrides) render as text                                                                                                                                                                                                                           |
| T2   | New or changed API endpoints, validation schemas, database migrations, new dependencies, CI/workflow changes                                                               | Full `security-officer` review                                               | Route tests for: schema rejection of bad/extra fields, authorisation (another user's id is denied), rate limit where applicable. New dependency: provenance check noted in the PR                                                                                                                                  |
| T3   | Authentication, sessions, password handling, invite codes, currency/ledger, pack grants and openings, game outcome logic, RNG, CSP/headers, compose/proxy/network exposure | Threat-model update in this file + full review + owner informed before merge | T2 tests plus an adversarial suite: replay, forged session cookie, concurrent double-spend / double-open, negative and overflow amounts, tampered outcome payloads, brute-force against the rate limit, and a dependency audit of anything new. For RNG and payouts: a statistical test against the published odds |

Severity decides depth: the test list above is the minimum, and the officer lengthens it when the blast radius is bigger than the tier's typical case. A T3 PR may merge the day it opens; the owner is informed through the PR's sign-offs (owner decision, 2026-10-30, which removes the earlier next-day rule).

Security tests live next to the code as `*.security.test.ts` and run in the normal test jobs (`quality` for `web/`, `api-tests` for `api/`), so a regression fails CI like any other test. Both jobs must be required checks in the live ruleset for that to hold.
